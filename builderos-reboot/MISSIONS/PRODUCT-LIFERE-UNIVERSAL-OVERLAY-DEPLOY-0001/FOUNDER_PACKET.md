# Founder Packet — LifeRE + Universal Overlay Deployment Closure

**Mission:** `PRODUCT-LIFERE-UNIVERSAL-OVERLAY-DEPLOY-0001`  
**BuilderOS:** BuilderOS 1 (Abbott)  
**Current priority:** Founder directive 2026-08-22 supersedes the prior SocialMediaOS-first execution order for this work session.  
**BuilderOS 2 (Castello):** ON ICE; no runtime or proof from Castello may satisfy this mission.

## Intention

Determine whether the existing LifeRE application and Universal Overlay can be treated as one deployable, usable system; close only the real remaining gaps; and prove the result in the canonical deployed reality without requiring ordinary founder operation.

This is a deployment-closure mission, not a new LifeRE product redesign and not a rewrite of the Universal Overlay architecture.

## Point A — measured current reality

- LifeRE has a previously completed Alpha corridor and existing runtime surfaces, including `public/overlay/lifeos-lifere.html`, LifeRE services/routes, and prior acceptance batteries.
- `docs/LIFERE_MASTER_BLUEPRINT.md` is an older architecture/blueprint-completeness target. It explicitly says its Point B is blueprint completeness, **not production app completeness**; it cannot by itself authorize deployment.
- Universal Overlay has substantial real implementation and deterministic A-to-Z tests.
- Universal Overlay SENTRY Layer B remains **not proven** in live reality. `products/receipts/SENTRY_OVERLAY_LAYER_B.json` currently records `LIVE_SESSION_NOT_PROVEN` because the drive session had no real extension-controlled browser tab polling it.
- The Universal Overlay product home records an architectural convergence gap: the general `taloa-runtime` BodyAdapter pipeline and the narrower A-to-Z `overlay-action-router` / `extension-drive-bridge` pipeline overlap and should converge rather than grow two real Body integrations.
- The previous governed factory exhausted 9/9 attempts on the Layer-B implementation slice. Evidence says the gate worked, but the slice was too large/complex for the available cheap codegen tier in one pass.

## Point B

A deployed LifeRE surface opens through the canonical LifeOS / Universal Overlay shell, authenticates correctly, has real Conductor conversation capability, reads real LifeRE state, and completes at least one bounded reversible overlay-driven action through a real browser/extension control path. The action is observed, selected, executed, independently verified, receipted, and visible in runtime truth. SENTRY Layer B returns a genuine PASS from a real browser session. No ordinary founder clicking or typing is required to manufacture the proof.

## Success rules

1. Do not call old LifeRE blueprint completion "app complete."
2. Do not convert deterministic fixtures into live-session proof.
3. Do not use Castello runtime, receipts, endpoints, or state as Abbott evidence.
4. Conductor is the canonical supervisory role name; `Chair` may survive only where a legacy code identifier must remain for compatibility.
5. If a free/cheap model fails a slice repeatedly, preserve its attempt evidence and **decompose or escalate the slice**; do not retry the same oversized instruction indefinitely.
6. Founder presence may be used for an optional usability review, but must not be a technical prerequisite for machine acceptance when a browser harness can prove the same property.
7. Every failed acceptance must write: what failed, why the system believed its action was correct, what evidence it missed, and the systemic prevention change.
